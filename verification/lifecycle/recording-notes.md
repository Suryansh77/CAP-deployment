## Verification-command corrections

Two follow-up commands in the recording did not provide valid additional proof.

### Application check

The disposable `kubectl run` application check returned:

    connect ECONNREFUSED

This was caused by using a newly created test pod inside the restricted Cap namespace. The test pod was not an appropriate representation of the already-running Cap Web workload under the namespace NetworkPolicies.

The Cap Web workload itself remained Ready/Running, and the installer had already completed its application-serving verification.

This is therefore documented as a verification-command error, not an application deployment failure.

### Full-deny follow-up command

The manually entered shell loop used to display the full-deny evidence produced a zsh parsing error.

The installer had already executed the full-deny test and archived its evidence independently.

The full-deny evidence therefore comes from the installer-generated verification artifacts rather than the failed display command.

### TLS follow-up display

The follow-up command used incorrect evidence filenames and therefore displayed no TLS output.

The clean installation generated the correct TLS interception evidence artifacts, including:

- `verification/egress/install-run-positive-tls-interception.txt`
- `verification/egress/install-run-positive-tls-proxy-log.txt`

The installer-generated artifacts are the authoritative evidence for the positive TLS interception test.
